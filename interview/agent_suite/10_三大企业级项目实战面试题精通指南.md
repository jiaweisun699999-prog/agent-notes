## 一、 项目一：携程 AI 智能助手项目 (Ctrip AI Assistant)

### Q1: [架构演进] 为什么项目早期采用自定义 ReAct Loop，后期切换为 LangGraph 状态机？解决了什么生产痛点？
**面试官提问意图**：考察你对 Agent 框架演进背景的理解，以及是否真正经历过大项目架构迭代。
**STAR 法则回答**：
- **Situation (背景)**：携程 AI 智能助手需处理机票预订、酒店查询、退改签等复杂多环节业务。早期基于 Python `while True` + LLM Tool Call 构建了自定义 ReAct 循环。
- **Task (任务)**：随着业务增加，自定义 Loop 出现死循环、状态丢失、缺少事务控制等瓶颈，需重构为高可控架构。
- **Action (行动)**：
  1. 将业务解耦为独立的子状态机（机票 Agent、酒店 Agent、用户验证 Agent）；
  2. 使用 LangGraph `StateGraph` 显式定义状态转迁与条件路由边 (`add_conditional_edges`)；
  3. 引入 Checkpointer 实现多轮对话快照与基于 `interrupt()` 的人工核验。
- **Result (结果)**：消除了 100% 的 ReAct 死循环案例，支持了状态回滚与时间旅行调试，多 Agent 协同成功率提升 35%。

**16K-22K 满分标答**：
> “自定义 Loop 的本质是**隐式隐性状态**，逻辑全部硬编码在 Python `while` 循环中，一旦面临分支分支嵌套、并行节点、Tool 报错重试或人工介入时，代码会迅速退化成‘面条代码’，无法做细粒度的状态持久化。
> 切换到 LangGraph 的核心收益是**显式图控状态 (Explicit Graph-driven State)**：
> 1. **图结构透明**：通过 `Nodes` 和 `Edges` 显式定义状态迁移，彻底规避死循环；
> 2. **持久化与断点**：自带 Pregel 引擎与 Checkpointer，原生支持 `interrupt()` 打断与 `update_state()` 恢复；
> 3. **多 Agent 嵌套**：可以将机票、酒店拆分为独立 Subgraph，实现作用域与状态隔离。”

### Q2: [多 Agent 协同] 携程项目中多 Agent 之间是如何进行上下文隔离与全局 State 共享映射的？
**面试官提问意图**：考察你对多 Agent 架构（Supervisor / Network / Subgraph）中的状态设计能力。
**16K-22K 满分标答**：
> “在携程项目中，我们采用了 **Supervisor 调度模式 + Subgraph 隔离** 的混合架构：
> 1. **全局 State (Global State)**：定义在父图中的 `CtripGlobalState`，仅保留通用公共字段，如 `user_id`, `session_id`, `messages`（使用 `Annotated[list, add]` 增量追加）, 以及当前激活的 `active_agent` 路由标记。
> 2. **局部 State (Local Subgraph State)**：各个专业子 Agent（如 `FlightAgentState`）继承公共基类，但扩展私有槽位（如 `flight_number`, `departure_date`, `seat_class`）。
> 3. **上下文隔离**：父图通过节点函数显式 `invoke` 调起子图，子图内部的临时检索日志、中间思维链 (CoT) 完全限制在子图局部作用域中，仅将最终结果（如订票成功确认单）回传给父图，避免全局状态污染。”

### Q3: [写操作安全性] 在携程机票/酒店订退款等写操作中，如何防止模型工具幻觉与事务失败？
**面试官提问意图**：考察对大模型“写操作”高风险场景的安全把控（Saga 事务模式 / HITL）。
**16K-22K 满分标答**：
> “对于机票下单、退款等金钱敏感的写操作，我们采取了**三重防线设计**：
> 1. **第一重：Tool 结构化入参严格校验 (Pydantic Validation)**：在工具执行前通过 Pydantic 对日期格式、身份证号、金额进行强类型与正则表达式校验，非法参数直接打回。

## 二、 项目二：RAG 企业知识库项目 (Enterprise RAG & MCP)

### Q4: [结构化解析] 面对包含多级标题、长表格的复杂 Markdown/PDF 文档，如何保证切片 (Chunk) 不丢失上下文？
**面试官提问意图**：考察对 RAG 预处理阶段高级切片算法（文档解析、层级继承、语义切片）的掌握。
**16K-22K 满分标答**：
> “传统固定长度切片（如 512 字符硬切）会导致段落与标题割裂、上下文丢失。我们在项目中采用了**‘结构化继承解析 + 语义动态切片’两阶段方案**：
> 1. **阶段一：标题层级树自动拼接 (`merge_title_content`)**：
>    利用 `UnstructuredMarkdownLoader` 解析出 HTML/Markdown 元素标签（`Title`, `NarrativeText`, `Table`），构建节点深度字典树。把当前段落归属的所有父级标题（如 `H1 > H2 > H3`）自动前置拼接至段落开头（例如：`[制度>考勤>请假] 请假需提前24小时申请...`），确保向量检索时携带完整路径语义。
> 2. **阶段二：基于向量变异度的语义切片 (`SemanticChunker`)**：
>    放弃按字符数切分，使用 `SemanticChunker` 按照句子滑动计算前后 Embedding 的余弦距离。当语义相似度出现显著骤降（超越 `percentile` 阈值）时才划定断点，确保每个 Chunk 都是语义独立的完整段落。”

### Q5: [混合检索与 RRF] 详细说明 Milvus 2.5 中 BM25 稀疏向量与 Dense 稠密向量的配置，以及 RRF 融合算法与 $k$ 值的调优。
**面试官提问意图**：考察向量数据库底层设计（Dense+Sparse 索引）、BM25 结合与 RRF (Reciprocal Rank Fusion) 数学原理。
**16K-22K 满分标答**：
> 1. **Milvus Collection Schema 设计**：
>    - 稠密向量字段 `dense`：`FLOAT_VECTOR(dim=512)`，使用 **HNSW** 索引（`M=16, efConstruction=200`）；
>    - 稀疏向量字段 `sparse`：`SPARSE_FLOAT_VECTOR`，绑定内置 `FunctionType.BM25` 函数，配置 `jieba` 中文分词器，创建 **SPARSE_INVERTED_INDEX** 倒排索引。
> 2. **RRF 混合检索算法原理**：
>    混合检索不依赖 Dense 与 Sparse 绝对相似度得分（解决不同得分子量纲不一致问题），而是基于文档在各路检索中的**排名 (Rank)** 进行倒数加权融合：
>    $$\text{RRF}_{\text{Score}}(d) = \sum_{i \in \{\text{dense}, \text{sparse}\}} \frac{1}{k + \text{rank}_i(d)}$$
> 3. **平滑因子 $k$ 值调优经验**：
>    - **$k=60$ (默认推荐值)**：赋予 Top 1-10 高排名文档极高的权重衰减比，适合强调精准匹配的问答系统；
>    - **$k=100$**：平滑排名之间的得差，使 10-30 名的文档也能获得合理暴露，适合多意图泛化检索。”

### Q6: [图控 RAG 进阶] 详细说明 CRAG (纠正型 RAG) 与 Adaptive RAG 在 LangGraph 中是如何实现动态节点流转与 Fallback 路由的。
**面试官提问意图**：考察高阶图控 RAG 架构设计能力。
**16K-22K 满分标答**：
> “传统的 RAG 是静态的（检索 ➔ 生成）。我们在项目中通过 LangGraph 构建了 **Adaptive / Self-RAG 图状态网络**：
> 1. **意图路由节点 (`Route Question`)**：通过带 `structured_output` 的分类模型判断问题类型，如果是实时新闻/外部天气跳转至 `Web Search` 节点；如果是内部规章制度跳转至 `Milvus Retrieve` 节点。
> 2. **文档质量评估节点 (`Grade Documents`)**：检索后进入 Grade 节点，由 LLM 判断检索出的 Docs 是否包含回答问题所需的信息。
> 3. **CRAG 纠正路由 (Conditional Edges)**：
>    - 若 `Grade == Yes`：直接跳转至 `Generate` 节点生成回答；
>    - 若 `Grade == No`（检索失效）：自动触发 `Transform Query`（查询改写节点）重构关键词，并路由到 Tavily 搜索引擎做外网检索 Fallback。
> 4. **幻觉与回答检测 (`Grade Hallucinations & Answer`)**：生成答案后检测是否存在幻觉（生成内容是否忠实于检索 Context），若存在幻觉打回重新生成，实现自愈闭环。”

### Q7: [MCP 协议] 项目中为什么引入 Anthropic MCP 协议？FastMCP Server 与 Client 是如何交互的？
**面试官提问意图**：考察对前沿 MCP (Model Context Protocol) 协议的实战落地理解。
**16K-22K 满分标答**：
> “**引入背景**：传统的 Agent 工具定义硬编码在项目内部，无法跨服务复用，且新增工具需要频繁重启 Agent 框架。
> **MCP 架构落地**：
> 1. **服务端 (FastMCP Server)**：将企业内部搜索、天气查询、计算器等独立能力解耦封装为 MCP Server，通过 `@mcp.tool()` 暴露，支持 **SSE (Server-Sent Events)** 远程传输协议；

### Q9: [限速与防 429] 批量调用大模型生成图像描述时触发 API 429 (Rate Limit)，架构中如何解决？
**面试官提问意图**：考察大批量数据处理时的并发控制、固定窗口限速与退避重试算法。
**16K-22K 满分标答**：
> “在处理百页 PDF 提取的上百张图片时，并发调用 API 极易触发 `429 Too Many Requests`。我们在底层 `my_llm.py` 中实现了**并发限速控制与指数退避重试**：
> 1. **固定窗口速率限制器 (`RateLimiter`)**：
>    使用 Python `threading.Lock` + 时间窗口锁，配置 `limiter = RateLimiter(max_calls=10, period=60)`（即限制每分钟最多 10 次调用），超限请求在锁内自动 `time.sleep()` 阻塞等待。
> 2. **带抖动的指数退避重试 (Exponential Backoff with Jitter)**：
>    捕获 429 异常后，计算退避等待时间：
>    $$\text{Backoff}_{\text{Time}} = \text{BASE}_{\text{BACKOFF}} \times 2^{\text{attempts}-1} \times (0.8 + \text{random} \times 0.4)$$
>    加入随机抖动系数 $(0.8 \sim 1.2)$ 避免惊群效应，最大重试 5 次，确保大批量多模态任务稳定无报错运行。”

### Q10: [自动化评估] 如何使用 RAGAS 框架对多模态 RAG 系统进行量化评估？核心指标是什么？
**面试官提问意图**：考察对 RAG 评估体系（RAGAS 框架、无 Ground Truth 评估）的建立与指标调优能力。
**16K-22K 满分标答**：
> “我们基于 **RAGAS 自动化评估框架** 建立了 RAG 效果 CI/CD 评测闭环（代码位于 `evaluate/evaluate_self.py`）：
> 1. **评估数据集构建 (`SingleTurnSample`)**：收集 100+ 真实用户提问，包含 `user_input`, `retrieved_contexts`, `response`（以及可选的 `reference`）。
> 2. **三大核心评估指标及含义**：

## 四、 项目实战：上下文工程 (Context Engineering in Projects)

### Q11: [项目上下文工程] 在 Agent/RAG 项目中，当工具返回巨量数据 (如 500KB JSON 或网页 HTML) 时，如何防止 Context Window 爆满与 Token 费用失控？
**面试官提问意图**：考察你在真实 Agent 项目中应对“超大工具返回值导致上下文爆满/高额 Token 账单”的防爆防击穿设计。
**16K-22K 满分标答**：
> “在 Agent 真实运行中，工具（如 API 搜索、网页爬取）经常返回数百 KB 的原始数据，直接丢进 `messages` 会迅速挤爆模型窗口，引发高延时与高费用。我们在项目架构中采用了**‘三级上下文瘦身与控制策略’**：
> 1. **第一级：Tool 返回值节点级剪枝 (Tool Result Pruning)**：
>    在 Tool 函数内部对原始 JSON/HTML 进行提取瘦身，仅保留核心字段（如将 500KB 网页 HTML 解析提取为 200 字符的核心正文摘要；将全量数据库记录精简为关键 ID 和 Key-Value）。
> 2. **第二级：指针句柄模式 (Handle/Reference Pattern)**：
>    当需要大文件处理时，Tool 不直接向 `messages` 返回原始数据，而是将巨量数据存入临时持久化存储 (如 Redis/S3)，仅向对话上下文返回一个指针句柄 `{"file_id": "doc_9921", "summary": "已获取 10,000 条订单"}`。后续节点需要时通过 Handle 针对性查询。
> 3. **第三级：基于 `trim_messages` 的消息滑动剪枝**：
>    在将 `messages` 传递给 LLM 之前，配置 `trim_messages(max_tokens=4000, strategy="last", token_counter=llm, allow_partial=False)`，确保发送给大模型的上下文始终维持在安全 Token 阈值之内。”

### Q12: [项目上下文工程] 生产环境中如何实现‘动态 Prompt 注入’与‘前缀缓存 (Prefix Caching / Prompt Caching)’加速？
**面试官提问意图**：考察上下文工程在提升推理速度 (TTFT)、降低 API 成本上的高级优化技巧。
**16K-22K 满分标答**：
> “1. **动态 System Prompt 注入**：
>    在 LangGraph 节点内，我们避免硬编码静态提示词。而是根据 `RunnableConfig` 中的 `user_role` (如 VIP/普通用户) 以及 `State` 中的当前业务阶段，动态拼接组装 System Message：
>    ```python
>    def agent_node(state: State, config: RunnableConfig):
>        user_info = config["configurable"].get("user_info")
>        prompt = f"你是一名专业的携程客服。当前服务用户等级：{user_info['level']}..."
>        messages = [SystemMessage(content=prompt)] + state["messages"]
>        return {"messages": [llm.invoke(messages)]}
>    ```
> 2. **前缀缓存 (Prompt Caching / Prefix Caching) 优化**：
>    - **原理**：底层推理引擎 (如 vLLM, Anthropic, DashScope) 会自动对相同前缀的 Token 进行 KV Cache 复用。
>    - **架构设计**：我们将‘固定的全局规则、不变的工具定义 (Tool Declarations)、长篇系统知识库’严格摆放在 Prompt 的最头部；将经常变动的‘当前轮次用户提问、实时变量’摆放在 Prompt 的末尾。
>    - **实战收益**：首 Token 响应时间 (TTFT) 从 2.5 秒降低至 350 毫秒（降低 85%），大模型 API 费用降低约 70%。”

## 五、 项目实战：多 Agent 架构模式选型与决策 (Multi-Agent Selection & Architecture Trade-offs)

### Q13: [多 Agent 架构选型] 面对不同业务场景，如何科学评估并选择多 Agent 的四大拓扑架构？
**面试官提问意图**：考察你对多 Agent 拓扑架构（Supervisor 路由模式、Hierarchical 分层子图、Network 去中心化 P2P、Sub-Agent 工具模式）的选型考量与权衡利弊。
**16K-22K 满分标答**：

| 拓扑架构模式 | 核心机制 | 适用业务场景 | 优缺点分析 |
| :--- | :--- | :--- | :--- |
| **Supervisor 模式** | 中央路由 Agent 统一接收请求，通过条件边分发给专有 Worker | 业务入口单一、分类边界清晰的客服分流系统 | **优点**：逻辑清晰、集中控制；<br>**缺点**：中央 Supervisor 易成为性能瓶颈 |
| **Hierarchical 模式 (分层子图)** | 父图编排大流程，复杂领域业务封装为独立编译的子图 | 跨领域大型项目（如携程机票+酒店+退款） | **优点**：强上下文隔离、团队并行开发；<br>**缺点**：嵌套层级深时调试成本高 |
| **Network / P2P 模式** | 去中心化，各个 Agent 之间可以直接互相调用与自由转交 | 专家协商、多轮交叉反思（如代码生成与 Code Review） | **优点**：高灵活度；<br>**缺点**：极端情况下容易引发死循环，必须配置最大步数限制 |
| **Sub-Agent as Tool 模式** | 将子 Agent 封装为 `@tool`，主 LLM 通过 Tool Call 触发 | 意图不确定、需模型自行决定何时调用子专家 | **优点**：零图编排侵入，复用 Tool 生态；<br>**缺点**：依赖模型对 Tool 的解析能力 |

## 六、 项目实战：大模型输出稳定性与高可用降级 (Reliability & Failover)

### Q14: [模型输出稳定性] 当大模型在项目中生成非法 JSON、缺少关键字段或 Tool Call 语法格式错误时，架构如何做自动纠错？
**面试官提问意图**：考察大模型生产环境容错与输出结构化自愈机制。
**16K-22K 满分标答**：
> “1. **绑定 Pydantic 结构化输出 (`with_structured_output`)**：
>    要求模型输出符合特定的 Schema，底层的 OutputParser 会校验 JSON 类型与字段存在性。
> 2. **自动纠错重试机制 (Re-ask Loop)**：
>    若大模型生成的字符串无法通过 Pydantic 校验并抛出 `OutputParserException`，我们捕获该异常，自动构建一条修正 Message 喂回大模型：
>    `"你上一次生成的 JSON 格式错误：缺少 'ticket_id' 字段，解析报错为：{error_details}。请重新纠正并生成正确的 JSON。"`
> 3. **降级模型重试 (Fallback Model)**：
>    如果重试 2 次依然失败，自动切换到精度更高、格式控制更强的主模型（如将开源 7B 模型切换为 Claude 3.5 Sonnet）进行二次解析，保证 100% 格式准确。”

### Q15: [高可用与灰度降级] 当主模型 (如 Claude/GPT-4o) 宕机、网络超时或触发限速时，项目架构如何实现无缝降级保活？
**面试官提问意图**：考察高可用企业级 LLM 架构设计能力。
**16K-22K 满分标答**：
> “在企业级生产部署中，大模型 API 随时面临网络波动、服务商宕机或 429/500 错误。我们实现了**三层高可用兜底架构**：
> 1. **第一层：模型级无缝降级 (`with_fallbacks`)**：
>    使用 LangChain 的 `with_fallbacks` 链式容错：
>    ```python
>    primary_llm = ChatOpenAI(model="gpt-4o", timeout=10)
>    backup_llm_1 = ChatAnthropic(model="claude-3-5-sonnet")
>    backup_llm_2 = ChatTongyi(model="qwen-max")
>    
>    reliable_llm = primary_llm.with_fallbacks([backup_llm_1, backup_llm_2])
>    ```
>    当 `primary_llm` 遭遇超时或 5xx 错误时，框架无缝透明地将请求切到备用大模型。
> 2. **第二层：节点级降级 (Exceptional Condition Edges)**：
>    若所有 LLM 均不可用，LangGraph 条件边捕获错误后跳转至 `fallback_rule_node`。
> 3. **第三层：规则引擎兜底 (Rule Engine Safety Net)**：
>    在 `fallback_rule_node` 中放弃大模型生成，使用基于正则或传统关键词的规则引擎返回友好的兜底提示：`'抱歉，智能助手暂时繁忙，已为您人工记录需求...'`，确保系统永不崩溃。”
