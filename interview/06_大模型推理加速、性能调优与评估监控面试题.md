# 🎓 大模型推理加速、性能调优与评估监控面试高频题 (全量进阶版)

> 本文档针对 16K-22K 岗位核心关注的 LLM 推理引擎 (vLLM/PagedAttention)、分布式并行推理、吞吐与首 Token 延迟调优、Token 成本控制与 LangSmith/LangFuse 生产环境监控。

---

## 一、 大模型推理加速与引擎 (vLLM / PagedAttention)

### Q1: 为什么常规部署大模型推理显存吞吐低？vLLM 引擎的 PagedAttention 解决了什么问题？
**标准回答**：
- **传统推理显存痛点**：
  - 传统 PyTorch 部署时，必须为每个请求在 GPU 显存中预先分配一块**连续的**静态空间用于存储 KV Cache。
  - 由于生成文本长度无法预知，预分配空间产生大量的**碎片化浪费**（显存利用率通常只有 20%~40%），极大地限制了并发 Batch Size。
- **PagedAttention 核心机制（参考操作系统虚拟内存与页表）**：
  1. 将 KV Cache 切分成固定大小的物理页块（Physical KV Blocks，如每块 16 个 Token）。
  2. 允许 KV Cache 存储在**不连续的** GPU 物理显存中。
  3. 通过动态维护“逻辑页 - 物理页表（Block Table）”，实现按需分配、共享物理页（如在 Beam Search 或 Parallel Sampling 场景下多个序列共享 Prompt 的 KV 页）。
- **效果**：将 GPU 显存利用率提升至 96% 以上，推理吞吐量提升 2~4 倍。

---

### Q2: 什么是 Continuous Batching（连续批处理 / 动态批处理）？它与传统 Static Batching 有何区别？
**标准回答**：
- **Static Batching（静态批处理）**：
  - 一组 Batch 中的请求必须等最长的请求生成完毕后才能统一结束并接收新请求。较短的请求早已生成结束，但显存和计算资源被迫闲置等待（Bubble 现象）。
- **Continuous Batching（迭代级批处理 / 连续批处理）**：
  - 在每个 Token 生成的**迭代步 (Iteration)** 层面进行 Batch 管理。
  - 一旦某个请求生成结束标记 `<eos>`，引擎会在下一个 Token 迭代步**立即将其踢出 Batch 并插入新的请求**，确保 GPU 永远处于满载高效状态。

---

### Q3: 什么是张量并行 (Tensor Parallelism, TP) 与流水线并行 (Pipeline Parallelism, PP)？多卡部署如何选择？
**标准回答**：
- **Tensor Parallelism (TP, 张量并行)**：
  - 将单层 Transformer 内部的矩阵乘法（如 Linear 映射、Attention 的 $Q,K,V$ 权重、FFN 权重）切分到多张 GPU 卡上并行计算（例如切分 ColumnParallelLinear 和 RowParallelLinear）。
  - 需要在单层前向传播过程中频繁使用 `All-Reduce` 进行 GPU 通信。必须依赖高带宽的 NVLink 互联（单节点多卡）。
- **Pipeline Parallelism (PP, 流水线并行)**：
  - 将模型按 Transformer 层切分（如 70B 模型共 80 层，卡 1 运行 1-40 层，卡 2 运行 41-80 层）。
  - 通信频次极低（仅在跨卡传激活值），适合跨节点、无 NVLink 的网络环境。
- **选型建议**：单节点 8 卡优先使用 TP（如 vLLM `--tensor-parallel-size 8`），跨节点大模型结合使用 TP + PP。

## 二、 性能瓶颈诊断：TTFT、TPOT 与 Token 成本调优

### Q4: 衡量大模型服务性能的核心指标有哪些？如何优化 TTFT (首字延迟) 与 TPOT (单字延迟)？
**标准回答**：
- **核心指标定义**：
  - **TTFT (Time To First Token, 首 Token 延迟)**：用户发起请求到看到输出第一个字的延迟（代表 Prefill 预填阶段性能）。
  - **TPOT (Time Per Output Token, 每个输出 Token 延迟)**：生成后续每个字所需平均时间（代表 Decode 解码阶段性能）。
  - **TPS (Tokens Per Second)**：系统单位时间吞吐量。
- **针对性优化方案**：
  - **优化 TTFT（缩短首字等待）**：
    - **Prompt Caching**：对公共的前置 Prompt / 系统指令进行 KV 缓存，避免重复 Prefill 计算。
    - **向量检索控制**：限制 RAG 检索返回的 Chunk 数量，控制输入 Token 长度。
    - **使用 FlashAttention 2/3**：加速 Prefill 阶段的高长上下文注意力计算。
  - **优化 TPOT（提高生成流速）**：
    - 使用 INT4/INT8 量化模型（减少解码阶段的 GPU 内存带宽瓶颈）。
    - 采用 Speculative Decoding（推测解码：轻量小模型预测 + 大模型并行验证）。
    - 使用高性能推理引擎（vLLM / TensorRT-LLM）。

---

### Q5: 什么是推测解码 (Speculative Decoding / Speculative Sampling)？
**标准回答**：
- **核心原理**：
  1. 使用一个极小的草稿模型 (Draft Model，如 680M 参数) 以极高流速自回归预测生成 $K$ 个 Candidate Tokens。
  2. 将这 $K$ 个 Token 连同原 Prompt 一起送入千亿参数的目标大模型 (Target Model) 进行**一次并行 Validation 前向传播**。
  3. 目标大模型并行校验 acceptance 接受前 $M$ 个符合概率分布的 Token。
- **优点**：由于大模型在验证模式下是并行计算 $K$ 个 Token，极大地榨干了 GPU 算力，在保证输出分布完全无损的前提下，将生成加速 2~3 倍。

---

### Q6: 如何在生产环境中降低 LLM 的 Token 调用成本与 API 延迟？
**标准回答**：
1. **语义缓存 (Semantic Caching)**：
   - 使用 GPTCache 等工具，将用户输入转换为 Embedding 在向量库检索。如果新请求与历史请求余弦相似度 > 0.95，直接返回历史生成结果，命中率可降低 20%~40% 的 API 支出与零延迟响应。
2. **模型分层降级路由 (Model Cascading / Tiered Routing)**：
   - 使用轻量级分类器评估任务难度：简单意图（如打招呼、简单分类）路由给便宜小模型（如 Qwen-2.5-7B / DeepSeek-V3），只有复杂推理解题才路由给高级模型（如 Claude 3.5 / GPT-4o）。
3. **Prompt 剪枝与上下文压缩**：
   - 提取检索到的 Chunk 核心句子，剔除冗余修饰词。

## 三、 Agent 监控与评估体系 (LangSmith / LangFuse)

### Q7: 生产环境下的 Agent 系统如何实现全链路 Trace 追踪与可观测性 (Observability)？
**标准回答**：
- **痛点**：Agent 系统包含多轮循环、工具调用、RAG 检索、状态更新，一旦出现回答质量下降或异常，极难排查是哪个环节出错。
- **解决方案（使用 LangSmith / LangFuse）**：
  1. **全链路 Call Tree（调用树）追踪**：记录请求进入系统的全过程——Prompt 原文、模型消耗 Token 数、响应延迟、调用的 Tool 名称及入参、RAG 检索出的具体 Chunk 得分。
  2. **Playground 调试与 Dataset 评测**：将生产环境的异常 Case 一键导入数据集，在 Web 端实时调整 Prompt / Temperature 重新测试。
  3. **用户反馈收集**：收集前端的点赞/点踩 (Thumbs up/down) 标签，与对应的 Trace 绑死，便于定位低质量回答的根因。

---

### Q8: 详细推导大模型预训练/微调/推理的 GPU 显存占用开销（计算公式与实战例题）。
**标准回答**（GitHub `mianshi7/LLM` 高频必考算力题）：
假设模型参数量为 $\Phi$（如 7B = 7,000,000,000），使用 FP16 (2 Bytes/Param)：

1. **纯推理阶段 (Inference VRAM)**：
   $$\text{VRAM}_{\text{Infer}} = 2\Phi + \text{KV Cache} + \text{Activation Buffer}$$
   - 7B 模型权重静态占用：$7 \text{B} \times 2 \text{B} \approx 14 \text{ GB}$。
   - 加上 KV Cache 和缓冲，推荐至少具备 18~20 GB 显存。

2. **全量训练阶段 (Full Fine-tuning VRAM)**：
   全量训练需要保存：
   - **模型参数 (Model Weights)**：$2\Phi$ Bytes (FP16)
   - **梯度 (Gradients)**：$2\Phi$ Bytes (FP16)
   - **AdamW 优化器状态 (Optimizer States)**：$12\Phi$ Bytes（包含 4 字节 FP32 副本 + 4 字节一阶动量 $m_t$ + 4 字节二阶动量 $v_t$）
   - **合计静态开销**：$2\Phi + 2\Phi + 12\Phi = 16\Phi$ Bytes（对于 7B 模型，仅静态开销就达 $16 \times 7 = 112 \text{ GB}$ 显存，必须配合 Zero-3 或多卡并行）。

3. **LoRA 微调阶段 (LoRA Fine-tuning VRAM)**：
   - 原始权重只读保存（14 GB），仅微调 0.1% 的可训低秩参数，优化器开销微乎其微。因此单卡 24GB 即可轻松微调 7B/13B 模型。
